## 已确认问题

### R1 / P1：账本只要存在预算，服务器月报依据读取就会报错

位置：`src/server/mcp-queries.ts:41`。

`snapshot()` 的 `planCashflowTotals` 是 `{complete:true, source:'posted_plan_transactions', rows:[...]}`，这里却直接对对象调用 `.some()` / `.find()`。因此实际已有预算的家庭无法正常读取月报依据、提交月总结或验证旧总结是否过期。

独立复现：`node work/mcp-migration/sol-budget-month-probe.mjs`。用正常草稿提交、采用流程创建 2026-12-05 的旅行预算，再读取：

```text
2026-11 ERROR state.planCashflowTotals.some is not a function
2026-12 ERROR state.planCashflowTotals.find is not a function
```

修复建议：读取并校验完整汇总的 `rows`；加入“有当月预算、有跨月预算、有当月发生付款的历史预算”三类组合验收。M005/M006 现有用例在无预算状态读取月报，未覆盖核心消费→月报链。

### R2 / P2：已含余额的历史补账没有进入各成员月度收支依据

位置：`src/server/mcp-queries.ts:31`（仅现金账户分录 JOIN）、`:34-37`；关联 `src/server/mcp-draft.ts:58`。

历史已含余额的收入/消费使用 equity + income/expense 分录，正确地不再次改变银行现金，但各成员依据只查询 cash 分录，因此整笔收入/费用消失。模型被要求根据 `memberCashflow` 比较各成员收支，会将有历史消费的成员遗漏。预付款转实际消费等无第二次现金分录的确认同样需要独立核算已确认收支，不能靠现金分录代替。

独立复现：`node work/mcp-migration/sol-probes.mjs`。登记现金 1000 元，快照日期 2026-11-01；通过正常草稿采用补记 2026-10-30 已含余额消费 12.34 元：

```json
{"memberCashflow":[],"journalExpenseMinor":1234,"cash":100000}
```

期望：银行现金仍为 100000 分，但该笔已确认消费在历史冻结归属成员的十月收支依据中可见，且明确与当月现金变动区分。建议提供按历史所有者、币种分列的 journal income/expense 或历史已含余额统计，而不是虚增现金变动。

### R3 / P2：周期草稿的证据变化后仍能直接采纳成不同金额规则

位置：`src/server/mcp-draft.ts:46-49`；候选身份生成见 `src/server/recurring-http.ts` 的 `id:'history:'+first.transactionId`。

提交时保存了 `candidateEvidence`，界面据此展示金额与证据；采用时只查同 `candidateId` 是否仍存在，随后使用新候选的金额、日期、证据写入。候选 ID 只由首笔流水确定，后续多月证据改变中位金额时 ID 不变。这使用户确认的界面内容与实际创建的规则不同。

独立复现：`node work/mcp-migration/sol-probes.mjs`。同账户、同说明在八/九月分别收入 100/110 元；草稿显示每月 110 元和两条证据。提交后增加十月 100 元，再采用原草稿：

```json
{"draftAmount":11000,"draftEvidence":2,"newAmount":10000,"newEvidence":3,"sameCandidate":true,"acceptedAmount":10000,"acceptedEvidence":3}
```

期望：证据、金额、日期、账户或归属变化均要求重新读取、重提并核对，原草稿保持 PENDING，不能生成不同于界面核对内容的规则。`autoPost=false` 限制了即时账务影响，但不能替代核对一致性。

## 建议追加的高优先级验收用例

1. C01：已有一笔当月/非当月预算，读取月报依据、提交/采用月总结，预算执行数字正确（R1）。
2. C02：成员A历史已含余额收入/消费、成员B普通现金收入/消费；按成员、原币月报一致，现金仅改变未覆盖部分（R2）。
3. C03：已预付款转消费：确认费用增加、银行不再扣款、成员消费可追溯，预算实付和已消费分别准确。
4. C04：周期候选在提交后新增一月证据使中位金额/日期改变：旧草稿采纳失败且不建规则；新稿重新核对后建待核实规则（R3）。
5. C05：已保存月总结→新增相关真实分录→浏览器旧总结标“依据已变化”；旧草稿无法通过确认；新总结替换的历史记录仍保留。
6. C06：两名有效家庭成员预算完全审批→同ID更新费用→第二成员旧票失效→旧版本投票失败→新版本完成审批；日历只一笔费用源，银行余额未变。
7. C07：两个真实家庭分别下载不同私有Skill版本、读取研究/月报；外家庭成员无法通过任何ID/版本参数读另一个家庭内容。
8. C08：管理员编辑/恢复Skill→下载ZIP内容及SHA与所选版本一致→临时目录首次安装/重复安装/覆盖备份→篡改正文、manifest路径、符号链接均失败；本机已安装内容在重新下载前保持旧版。
