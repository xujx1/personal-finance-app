## 2. AI消费助手：一个交互，清单驱动预算

### 2.1 状态机

`想法输入 → 类别识别 → 补齐必要信息 → 只读财务查询 → 行程/采购/商品检索 → 可编辑消费清单 → 本人核对清单 → 重新计算金额 → AI复核 → 本人确认预算 → 实际付款/退款`

- 旅行研究、商品比价、餐饮采购都是同一次预算生成中的内部节点，不再各自提供独立研究表单。
- 类别优先自动识别，允许用户调整；关键词只作预识别，AI生成时复核。不能把“买菜”误当普通电商购物，也不能因一句“去过旅行”直接创建新计划。
- 查询资产、负债、目标、预算和历史只允许读取当前有权访问的账本。缺少事实就提问，不造工资、房贷或汇率。
- 页面显示“核对资产 / 负债 / 目标 / 近期消费”等执行状态和流式分析，不显示原始工具响应、完整账户标识或模型内部推理。
- 任何流式片段都不是可批准结果。只有完整响应、结构校验、金额重算、版本与期限校验全部通过后，才能开放本人确认。

### 2.2 旅行清单模型

消费草稿包含 `kind`、`itinerary[]`、`items[]`、`comparisons[]`、`reviewed`、`totalMinor`。

| 对象 | 字段与规则 |
| --- | --- |
| itinerary | date、time、title、notes；下一步补稳定id与预算项目关联id，不能把候选列车写成已出票 |
| items | id、category、name、quantity、unitPrice、amount、selected、sourceUrl、sourceType、note |
| category | 机票、火车票、燃油、高速、停车、住宿、早餐、午餐、晚餐、门票、亲子体验、宝宝用品、应急、其他 |
| sourceType | scenario_estimate（情景估算）、user_quote（用户报价）、retrieved_reference（检索参考）；都不意味着已付款 |
| totalMinor | 仅对 selected 项求和；先精确计算数量×单价，再按分舍入；不使用浮点累计金额 |

用户可修改出行日期、酒店、交通、餐饮、数量、单价，或取消某个项目。每次变更立即更新草稿合计，并使旧的AI通过状态失效；调整后重新评估，再确认预算。出行日期/人数变化导致路线假设变化时，重新生成相关方案，不只改一个总数。

安徽亲子游验收：妈妈下班17:30、约19点杭州西站高铁会合；总成人数要包含晚间会合者；照顾宝宝13:00–14:30午睡；酒店、车票、油费、通行费、停车和餐饮分项；候选绩溪/黄山只选一个正式执行方案。上述是用户场景，不默认已成行。

### 2.3 商品比价

比较记录包含商品/版本/平台/语言/新旧、商家、价格、运费、到手价、链接、查询时间、可比性和售后备注。规格不同必须单列，不能只按价格排序。

识别链接和图片后检索同款。JD卡带¥278、二手¥234为用户提供的历史场景，不是本站已核实的当前市场价；已购《王国之泪》应在偏好与历史里核对，避免重复推荐。没有检索依据时标记未知，不生成虚构商家和报价。

### 2.4 与后端衔接

Mac本轮已接通类别预识别、ExpenseDraftEditor、研究结构化清单、服务端复核和采纳保存链路；外部模型配置缺失时不声称真实AI通过。

已实现的Mac接线（下列为验收边界，不代表真实外部能力联调）：

1. `research-http.ts` 产出结构化 itinerary/items/comparisons；引用限定为实际检索或用户提供的来源。
2. `AdvisorPanel.tsx` 展示可编辑清单；先由用户核对，之后再调用最终预算评估，不能生成后立刻跳过清单确认。
3. `advisor-http.ts` 对用户调整后的草稿再次调用 `normalizeExpenseDraft`，使用服务器重算总额；不能相信客户端的 totalMinor。
4. `advice.accept` 把审核过的清单、行程、来源和正式预算一并保存。清单修改后旧建议不可复用。
5. `PlanDetails.tsx` 调整清单时回到AI助手复核，不在后台悄悄改正式预算。

### 2.5 生活日历（Mac增量，已实现查看）

使用与预算页相同的已保存plan文档，做只读日历投影。每周从周一开始，业务日期按Asia/Shanghai解释；支持月/周、月份跳转和今天，周末突出。可筛旅行/餐饮、显式显示取消记录；日期缺失或无效的计划列为待排期。支持年份0001—9998，越界月份和相邻格不能触发无效日期。

跨日计划每天显示同一计划的摘要；选中日展示已保存的`itinerary[]`对应明细，未提供时明确提示，不从研究长文本猜餐次、车次或具体活动。不按天拆分/累加整项预算，不改变预留或现金；点击原计划详情继续既有付款/提醒流程。新增计划跳转AI消费助手并带入所选日期。新增餐饮预算分类，并在消费类别为餐饮时默认对应确认分类。

本增量不包含日历内编辑、拖动改期、三餐表单或AI结构化清单保存链路；这些仍按2.4及R09继续。无需数据库迁移、日历第三方服务或外部日程同步。验证证据见执行清单的“Mac增量：生活日历”。

## 3. AI投资助手：一个交互，工具节点驱动

目标流程：`投资问题 → 资产/负债查询 → 已有预算与现金流查询 → 持仓与集中度 → 目标和近期行为 → 最新可用行情/汇率 → 网络理财研究 → 流式结论和风险情景`。

登记已有资产也是助手内部任务，只有明确登记时才展开必要资料，不因“想买NVDA”自动增加持仓。

Mac本轮已将InvestmentPanel作为投资主入口，资产登记为显式内部入口，已移除独立ResearchWorkspace主表单接线。

拟统一只读工具：get_assets、get_liabilities、get_budgets、get_holdings、get_savings_goals、get_recent_consumption、get_cashflow_context、get_market_quotes。当前已有前五类财务查询中的资产、负债、目标、历史和现金流工具；预算、持仓和行情的统一工具仍待接入。工具不提供任意SQL、任意URL代理、批准预算或付款能力。

| 事件 | 字段 | 页面行为 |
| --- | --- | --- |
| tool | name、status=running/completed | 只显示查询进度；不渲染原始财务JSON |

OpenAI官方当前要求此推理流使用 `https://api.openai.com/v1/responses`、`store:false`、`stream:true`，HTTP中显式携带所需历史；身份登录不等同推理授权。函数工具按namespace声明，客户端执行只读工具后回传结果；不能把服务端托管MCP工具直接当作这条OAuth推理通道的可用能力。Web搜索是否可用取决于模型及账户/工作区策略。[1][2][3]

## 5. 公网站点、账号打通与家庭关系：调研结论及后续方案

### 5.1 公网可达和财务公开是两件事

建议当前继续“公网可达、登录后受控访问”，保持现有Sites私有受众。没有家人权限与数据隔离前，不能将财务站改成匿名公开站。

Sites原生登录已经解决本站访问身份；可信用户ID在同一个Site内稳定、跨Site不同，不能假定等同于独立OAuth返回的sub。邮箱只是展示/联系字段，不作唯一授权键。自部署时不能信任客户端自行传入的Sites身份头。

当前代码的 `bookId='personal'` 是单账本实现。若公开给多个已登录用户，当前机制不足以提供多家庭隔离。尤其不能把“所有者未配置时允许写”当作多用户授权策略。

### 5.2 ChatGPT的三种接入必须区分

| 通道 | 解决的问题 | 条件与边界 |
| --- | --- | --- |
| Sites原生ChatGPT登录 | 谁能访问本站 | 沿用平台登录与分享控制；不另搭一套Sites登录 |
| ChatGPT OAuth推理 | 本站使用个人ChatGPT计划能力 | 需单独符合资格并授权；本地动态注册回调是127.0.0.1；不能直接把本机回调换成任意公网站址 |
| ChatGPT→本站MCP | ChatGPT读取本站并提交研究草稿 | 当前仅本地工具测试；站点先发布，之后才能连接官方私有插件；不开放审批/扣款工具 |

独立网站的官方身份OAuth需要已注册客户端和精确回调；官方当前说明其商业网站登录处于受限试用，不能承诺任意公网应用都可自助接入。[4]

对于个人远程VM，官方说明本机127.0.0.1回调到浏览器所在电脑；需要先在本机完成授权，再通过安全通道迁移受保护的凭据及元数据，并由VM维护刷新。当前项目未实现这一迁移流程，也不能用复制浏览器Cookie来替代。[5]

### 5.3 AI依赖清单

| 能力 | 当前适配 | 公网部署需要 |
| --- | --- | --- |
| 文本分析/结构化预算 | OpenAI-compatible Chat Completions，用户指定qwen3.8-max尚未真实联通 | NEW_API_BASE_URL / MODEL / KEY，或另行授权的ChatGPT推理 |
| 网络检索与比价 | Tavily适配，或ChatGPT Web搜索 | Tavily密钥；或者模型与账户允许的Web搜索能力；模型本身能聊天不代表能联网 |
| 图片识别 | 显式视觉模型 | NEW_API_VISION_MODEL；不能假定文字模型具备视觉能力 |
| 行情/汇率 | 腾讯/基金公开接口、ECB | 网络可达、超时缓存、日期与延迟说明；公开接口不保证实时或SLA |
| 保存票据 | 服务端AES-GCM加密，小附件存D1 | 独立ATTACHMENT_KEY；原图识别默认不持久保存 |
| 后台任务 | 本地周期检查与/jobs处理器 | Sites受支持的计划任务/服务访问，或自部署调度器；不能依赖浏览器页面一直开着 |

所有凭据仅保存在服务端安全配置。未来家庭模式默认各用户的OAuth连接独立，不共享refresh token；若使用家庭服务端API额度，需显式共享配置和家庭预算限额，不能默默借用家庭管理员的个人ChatGPT授权。

### 5.4 多家庭数据隔离设计（未实施）

推荐先做显式家庭membership和应用层强制过滤；规模扩大时，可评估每家庭独立D1数据库。Cloudflare官方支持按租户数据库或共享数据库内隔离两种结构，选择不代表已经自动获得行级授权。[6]

| 新增/调整对象 | 关键设计 |
| --- | --- |
| users / identity_links | 本站用户与可信issuer、clientId、subject的映射，三者唯一约束；不靠邮箱自动合并 |
| households | 家庭ID、名称、创建者、状态 |
| household_members | householdId + userId唯一；owner / approver / member / viewer；生效与撤销状态 |
| household_invites | 一次性邀请token只存hash，限定家庭、角色、有效期和使用状态 |
| books | 新增householdId；每家庭的active_dataset/revision/fence独立 |
| 财务表 | 所有读取/写入、文档、命令、附件、缓存与审计都带book/household范围；外键和唯一约束防跨家庭引用 |
| oauth_connections | 按用户与provider隔离加密凭据，授权范围、到期和generation；不放进财务备份 |

每个请求先验证登录，再检查家庭成员资格，再在授权范围内查具体对象。家人成员关系不能等同于可读所有私人资产。可增加“个人账本”和“家庭共享账本”，必须显式共享或转入，避免夫妻独立资产被默认合并。OWASP建议默认拒绝、逐请求校验，并对猜测对象ID的越权访问做测试。[7]

### 5.5 家庭关系与审批（未来设计）

支持创建家庭、邀请、加入、离开、移除、转移所有权；“配偶/父母/孩子”等家庭称谓和权限角色分开。未成年人可只是无登录能力的受益成员。已发生交易不因成员离开而删除。

未来可选家庭审批：申请人提交草稿 → AI评估 → 有权限的成员批准 → 按预算记实际付款。AI建议不是用户权限，也不是银行付款授权。审批绑定预算版本、金额、币种、对象及账本修订，变更后原审批失效。

隔离验收必须覆盖：A家庭猜B家庭计划ID、附件ID、AI历史ID、备份ID；只读成员写入；移除成员后的旧会话；跨家庭退款/转账；后台任务写错家庭；OAuth凭据串用；恢复备份后旧写入继续提交。家庭功能尚未授权进入本日实现，先作为明确技术方案留存。
